The promise and its limits

The signing path is the gate.

If every usable fee-signing capability is confined to this trusted wallet path, an untrusted dapp cannot skip its checks. A small balance is then a loss limit for failures of that boundary, not a requirement for normal dapp isolation.

Proved in a small abstract Lean model

No substitution. No second release.

The modeled gate releases the same snapshot that passed checking. A spent request is terminal. Every released snapshot satisfies the declared predicate, assuming the checker is sound.

This is a proof of the transition model. Connecting all browser/Rust executions to that model is not yet proved.

Does the fee reservoir still matter?

Your reasoning is correct: if the key is exclusively accessible through this enforced path, the dapp cannot use it outside that path. A small reservoir becomes optional defense in depth against wallet bugs, a compromised signing host, leaked recovery material or repeated otherwise permitted sponsorship.

A per-envelope fee cap is not a total spending allowance. Aggregate limits need persistent, rollback-resistant accounting. Unrestricted automatic refills remove the reservoir’s loss cap. A shared seed compromise also exposes U; a small F balance does not protect U.

03 / Pick the boundary you need

Local convenience or enforced sponsorship.

A “fee-only” native signer is only a partial restriction. Low-threshold authority also covers actions such as bumping the account sequence.

Fully local option

A small fee reservoir

Give L weight 1. Set F’s low threshold to 1 and medium/high to 2; keep an administrative key with weight 2.

If exclusivity is required

An indispensable wallet boundary

Use a separately trusted wallet origin, signer service or capable secure hardware that verifies the pinned passkey, C authorization, exact fee envelope, freshness and budget before signing.

The calling dapp must lack a sufficient fee-signing key or quorum. The popup above enforces this against that dapp, while trusting its wallet host. Every native signing route—including administration and recovery—must fit the stated trust assumptions.

Enforce independently; keep Cedar as the policy language.
No native fee allowance: a token allowance from G to C does not authorize Stellar network fees. Use a prefunded F account or an enforced sponsorship budget. Passkey PRF can unlock a local key, but it does not prevent another use after unlock.
What this example establishes—and what still needs work

The bypass is a constructive counterexample to “a callable local fee key can only sponsor C.” The guarded API is tested for identity, challenge, fee and replay checks. The WASI path also has a separate abstract Lean model; the implementation and ledger execution are not formally verified.

A stronger theorem would be conditional: with every sufficient fee-signing route constrained, uncompromised keys, a correct isolated verifier and fresh approval records, every issued fee signature corresponds to an approved envelope. Stellar cannot identify which UI produced a signature.

The earlier authority-kernel proof campaign does not cover Cedar, WebAuthn, fee sponsorship or this prototype.
