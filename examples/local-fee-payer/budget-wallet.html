    One passkey. A separate funding limit.

    The wallet asks C to execute the fixed refill adapter. Native Perch checks C’s owner passkey. The budget then computes the refill from F’s real balance and its remaining lifetime cap.

    Changing a Perch document or renewing the treasury allowance cannot reset the budget or change F. The budget has no recipient setter, reset or upgrade entry point.

    How this fits Perch dev

    This lab uses native Perch’s owner rule 0. Production can give the adapter a dedicated document grant using existing function and authorization-root constraints. The reusable budget is the settlement component; there is no OZ policy callback or new fee-budget document keyword. This fixed owner shell has no document mutation or upgrade endpoint.

    What the proof says.

    For every input to the extracted Rust refill function, an accepted plan pays the registered recipient, increases cumulative spending by exactly that amount, and never exceeds the cap. It also requires a low balance and an unexpired budget. The contract exposes no destination, amount, reset or upgrade argument.

    Token transfers, authorization and failure rollback are checked in contract tests and local ledger execution. Lean does not prove the Soroban host, Perch, browser, compiler or cryptography. The cap applies to this contract’s refills—not bootstrap funds, unrelated deposits or all spending from F. F’s native key is still capable of signing elsewhere if the trusted wallet or seed is compromised.

    No silent renewal: when a refill cannot fit, it stops. Replenishing the SAC allowance does not reset spending. Budget renewal or F rotation would require a separately authorized design.
