nido

Passkey-native smart accounts for Stellar

An open account-abstraction stack: Soroban contracts, a browser wallet, and a TypeScript SDK that move users from G-addresses to passkey-secured C-addresses — with every authorization verified on-chain.

→ / ← to navigate · a technical tour for the team

Why

A G-address is its keypair — that's the problem

  • Key loss is account loss. One ed25519 seed, memorized as 24 words. Lose it and the account is gone; leak it and the funds are gone. No undo, no recourse.
  • Auth logic is fixed by the protocol. Classic accounts give you signers + weights + thresholds — and nothing else. No spending limits, no session scopes, no time locks, no custom recovery.
  • Seed-phrase UX filters out normal users. "Write these words on paper and never lose them" is the onboarding step where most people quit — or hand their keys to a custodian.

What we actually want: login that feels like Face ID, permissions that are programmable, and recovery that doesn't depend on a company holding your keys.

Account abstraction

Smart accounts: the account is a contract

A C-address with a custom __check_auth — authorization becomes code you write, not a protocol rule you inherit.

How Soroban invokes it

When a transaction needs the account's authorization (require_auth), the host calls the account contract's __check_auth with the signature payload hash, the signatures object, and the auth contexts being authorized. Panic = deny: if the code aborts, the auth fails.

Nido builds on OpenZeppelin stellar-accounts rather than reinventing the auth kernel.

Passkeys

Why passkeys are the right first signer

  • Hardware-backed P-256, no seed phrase. WebAuthn credentials live in the platform authenticator (Secure Enclave / TPM), sync via iCloud or Google, and sign only after biometric user verification.
  • Phishing-resistant by construction. The browser scopes each credential to its RP ID and embeds origin + challenge in the signed payload. A look-alike site can't request a valid signature.
  • And Soroban can verify them natively. The secp256r1_verify host function checks P-256 signatures on-chain. So the chain itself — not a backend — verifies every WebAuthn assertion.

Formats we care about

Public key — 65-byte SEC1 uncompressed (0x04 ‖ X ‖ Y).

Signature — DER from the browser, converted to 64‑byte compact r ‖ s, low-S normalized (one canonical encoding per signature) before it goes on-chain.

Architecture

The stack at a glance

  • Wallet app — packages/frontend, an Astro app at nido.fyi. Each account lives at its own subdomain: <C-address>.nido.fyi.
  • Passkey SDK — @nidohq/passkey-sdk: WebAuthn parsing, auth-digest computation, signature injection, deploy, recovery, session keys.
  • Wallets Kit module — NidoModule for stellar-wallets-kit; Nido appears in dApp wallet selectors next to Freighter & xBull.
  • Soroban contracts — Factory · Smart Account · WebAuthn Verifier · Multisig + Spending-Limit policies · ZK Recovery pool/controller · UltraHonk verifier · Name registry (human-readable account names).
  • Infra — OpenZeppelin Relayer (gas abstraction, nido.fly.dev) and a Cloudflare Worker pool indexer that mirrors the recovery Merkle tree.

Everything auth-critical is on-chain; the off-chain pieces only carry bytes or cache public state.

Onboarding

Factory: deterministic C-addresses, atomic genesis

// contracts/factory — the address is a pure function of
// (factory, salt, wasm hash). Constructor args don't affect it.
pub fn get_c_address(e: &Env, salt: BytesN<32>) -> Address {
    e.deployer().with_current_contract(salt).deployed_address()
}
  • Reserve first, deploy later — the wallet computes the C-address up front, so a G-address can fund it before the contract exists.
  • One transaction — create_account_v2(salt, key, commitment) deploys the account, installs the passkey as first signer, and inserts a recovery-pool leaf. Any failure reverts everything.
  • Embedded wasm — the factory embeds the smart-account wasm via include_bytes! and hashes it at runtime; no hardcoded hash to drift.

Trust-minimized by design

Deterministic derivation means the factory can't swap in different code for your address — the wasm hash is part of the address math.

Shared contracts (verifier, ZK recovery) resolve by name through the Stellar Registry — the ecosystem's on-chain contract directory, distinct from Nido's own name registry — and are cached in instance storage.

The account contract

Anatomy of a Nido smart account

impl CustomAccountInterface for NidoSmartAccount {
    type Signature = AuthPayload;  // signers + context_rule_ids

    fn __check_auth(e: Env, signature_payload: Hash<32>,
                    signatures: AuthPayload, auth_contexts: Vec<Context>)
        -> Result<(), Self::Error> {
        do_check_auth(&e, &signature_payload, &signatures, &auth_contexts)
    }
}

Three OpenZeppelin traits: CustomAccountInterface (auth), SmartAccount (manage signers/rules/policies, each self-authorized), ExecutionEntryPoint (generic execute).

Context rules — the mental model

An account is a list of rules. Each rule = scope (Default, or CallContract(X)) + signers + policies.

  • Constructor installs a Default rule holding your passkey(s).
  • Policies attached to a rule all must pass.
  • A zero-signer rule + one policy makes the policy the sole authority — remember this for recovery.
On-chain WebAuthn

Verifying a passkey assertion on-chain

The stateless verifier contract (deploy once, shared by all accounts) receives the raw assertion and replays the WebAuthn math:

  1. Parse clientDataJSON (the browser's record of the sign request); require type == "webauthn.get"
  2. Require challenge == base64url(auth digest)
  3. Check the flags in authenticatorData (the authenticator's own bytes): UP + UV — user present, user verified
  4. Digest = authData ‖ sha256(clientData)
  5. secp256r1_verify(pubkey, sha256(digest), sig) — the host function does the P-256 work

The challenge is not just the tx hash

OZ v0.7 signs one step past Soroban's signature_payload:

digest = sha256(payload ‖ context_rule_ids)

The signature is bound to the specific rule it authorizes — a signature collected for a scoped session rule can't be replayed against the default rule.

Origin, rpIdHash, and sign-count checks are deliberately omitted on-chain — the browser enforces origin scoping; the chain verifies possession + intent.

Subdomain-per-account

The WebAuthn RP ID is the account's own subdomain — passkeys are cryptographically scoped to one account at the DNS level. Wrong account? It surfaces ACCOUNT_SWITCH_REQUESTED.

Scope

Soroban-only: one InvokeHostFunction op per tx. A Nido C-address cannot sign classic Stellar operations. Multi-signer rules (N-of-N, M-of-N) sign the same digest.

Programmable auth

Policies & session keys: auth as composable rules

  • Multisig policy — M-of-N threshold over a rule's signers (SimpleThresholdAccountParams). Powers friend-based recovery via add_multisig_recovery(…).
  • Spending-limit policy — a rolling-window meter over SAC (Stellar Asset Contract) transfer calls in scoped contexts: a limit per ledger period (~5-second blocks). Updates preserve the current window.
  • Session keys — not a contract, a scoped signer: a second WebAuthn credential installed on a narrow rule (e.g. one dApp, spending-limited), default 30-day expiry.

The composition rule that unlocks everything: policies on a rule AND together, and a rule with zero signers and one policy makes that policy the rule's sole authority. That's the hook ZK recovery hangs on — coming up next.

Recovery

Lost passkey ≠ lost account — but how, exactly?

Platform sync fails, devices die, Apple IDs get locked. If passkeys are the only signer, we've just rebuilt the seed-phrase cliff with better UX. Recovery needs to exist — under constraints:

  • No custodian. No company that can take the account — or be subpoenaed, hacked, or shut down into taking it.
  • No social graph leak. Guardian schemes publish who your friends are and require coordinating M-of-N humans at the worst possible time.
  • Owner keeps the veto. A thief who finds your recovery secret shouldn't be able to instantly drain the account.
  • No linkability. Enrolling in recovery shouldn't mark your account on-chain as "has recovery" — or link it to anything else.

Social recovery exists in Nido today — an M-of-N friends rule via the multisig policy (add_multisig_recovery). It's a solid opt-in, but friends churn, collude, and get phished — so it can't be the only path. For everything above, we need something trustless — that's ZK recovery, next.

ZK recovery — the idea

A coat check, cryptographically

You hold a claim ticket (a secret); the pool holds a stub bound to your account (a commitment). To recover, you prove you hold the matching ticket — without showing it.

  • Secret → seed words or a deterministic wallet signature (same input, same bytes), HKDF-derived in-browser into a BN254 field element — a number in the proof system's native format. Never stored anywhere.
  • Commitment → Poseidon2([DOM_LEAF, secret]) — a ZK-friendly hash of the secret plus a fixed domain tag — wrapped on-chain with your account address, appended to a depth-24 Merkle tree (~16.7M leaves).
  • Proof → "some leaf in this tree is bound to this account and I know its secret" — plus a nullifier so each secret spends once, and an auth hash binding every argument of the request.

Uniform anonymity set

Every account gets exactly one genesis leaf — real, or a deterministic dummy (sha256("nido-zk-dummy" ‖ salt) mod r, folded into the same field). On-chain, enrolled and non-enrolled accounts are indistinguishable.

What the circuit does not know

The circuit — the fixed program the proof attests ran correctly — sees no guardians, no votes, no balances. Public inputs are just root, nullifier, auth_hash — membership, uniqueness, and request-binding. Nothing else.

ZK recovery — the flow

Initiation needs no key and no funds

No require_auth — the UltraHonk proof is the authorization, and the OZ relayer pays the fee. Verified fully on-chain via BN254 host functions: ~159M CPU of the 400M budget. Rate-limited to 3 attempts per rolling 90 days.

The owner keeps the veto

During the timelock (mainnet: a 14-day delay, never configurable below the 7-day floor) the real owner can cancel — or burn_nullifier forever — each requiring their own proof, so strangers can't grief.

Completion is a policy gate, not a proof

The recovery rule is zero-signer with the ZK controller as sole policy. Completion is a plain add_context_rule installing only the pending new passkey; enforce checks the stored record, exact call shape, and timelock.

Off-chain: a Cloudflare Worker mirrors the tree from LeafInserted events (Soroban RPC nodes — the chain's query servers — keep only ~7 days of them); clients verify against the on-chain current_root before proving.

Integrate

Adding Nido to a dApp is a module import

import { StellarWalletsKit } from '@creit.tech/stellar-wallets-kit';
import { NidoModule } from '@nidohq/stellar-wallets-kit-module';

StellarWalletsKit.init({ modules: [
  new NidoModule({
    base: 'https://nido.fyi',
    networkPassphrase: 'Test SDF Network ; September 2015',
  }),
  /* Freighter, xBull, Albedo, ... */
]});

What the module does

signTransaction opens the account's /sign/ page, simulates to locate the auth entry, computes the OZ auth digest, runs the passkey ceremony, injects the signature, and hands signed XDR back.

The dApp never touches WebAuthn or auth-entry surgery. Full walkthrough: docs/ADD-NIDO-TO-DAPP.md.
