Before the requested action

Low balance triggers a refill request

The wallet starts it. Perch authorizes it. The funding contract recomputes it.

01 · Read

Is F below its low mark?

Read F and its registered budget. No refill is needed while the balance is sufficient.

02 · Refill

Approve C’s refill call

The budget rereads F’s balance and sends target − balance only to F, if the remaining cap covers it.

03 · Continue

Wait, then run the action

Confirm the refill before preparing the action. F pays the native network fees.

F must be funded before it can pay for a refill. Top-ups still need passkey approval. The cap covers this deployment’s refills, not initial funding or other deposits; it is not a ledger-enforced “fees only” restriction on F.

Proposed partner role

Turnkey can control the treasury.
F stays in the user’s wallet.

  1. Turnkey: treasury authorizationConsent to enrollment, approve the token allowance, and pause funding if needed.
  2. Perch: on-chain funding limitsFixed F, cap and expiry; renewing allowance does not reset spent.
  3. Wallet: everyday signingLocal U/F keys and direct RPC submission. F never goes to Turnkey.

The partner ask: help authorize and manage a bounded treasury grant, without joining every transaction’s signing path.

Proposed, not integrated with Turnkey yet. The current lab uses a standalone G treasury. A C treasury is another integration choice, not demonstrated here. A token allowance funds F; it is not a native fee-payment allowance.
